# Adapter: coding / working agents (Claude Code, Codex, Gemini CLI, ...)

Two distinct roles run on agentic tools. Any vendor works; switching vendors changes nothing outside this file.

## Role 1: writer (kind: mechanical)

Applies a RESULT's `state_changes` to `live/**` and commits.

Contract:
- Input: one complete RESULT packet. A bare `state_changes` section is incomplete because replay identity, G9/G10, owner-verdict/G5 and local `next`-handoff validation require the full packet; bounce it before writes.
- Apply the RESULT's declared state-change intent atomically against fresh current state; append the log line once to LOG.md (lane-mode prefixes lane id after session-id); save the full RESULT once to `history/<date>-<session-id>.md`; commit with a descriptive message (`<direction>[/<track>] <play> <node/task>: <log line>`).
- Maintain the `END_OF_FILE: <path>` trailer on every state file it writes (truncation guard, schema/direction-files.md).
- **Fresh-state semantic rebase is mandatory.** Re-read every target immediately before apply. Blob/SHA/commit ids, expected old text and exact anchors in `state_changes` are the base for a three-way rebase, not freshness locks. A mismatch by itself is information that concurrent state landed, never a reason to bounce. Derive only the RESULT's explicit delta, locate targets by stable path/id/key, apply that delta to the current files, and preserve every concurrent change outside those targets. `Preserve unchanged` means preserve the current value after rebase, not restore the packet's base. Compatible edits to a named target are merged; moved anchors are relocated by their stable identity.
- **Bounded integration judgment only.** The writer may resolve stale anchors and compatible parallel updates; it may not invent or alter outcomes, evidence, owner verdicts, gates, tasks, CALL meaning, or unrelated state. Compare base-to-RESULT and base-to-current at semantic-field level: shared path/id or whole-object inequality alone is not a collision.
- **Bounce threshold.** Bounce only when the RESULT or its local `next` handoff is invalid/incomplete under the checks below, the intended delta is itself ambiguous, or a fresh-state rebase leaves mutually exclusive meanings for the same semantic field (for example, the returning call was consumed by a different RESULT, or a named target was deleted/retargeted so the declared outcome is no longer meaningful). Report that semantic conflict. Never bounce merely because commits, blobs, anchors, `updated:`, unrelated tasks/calls/tracks, or an obsolete global-routing instruction changed meanwhile.
- **Whole-RESULT replay is idempotent.** Before normal apply, look up the committed history path for the incoming session-id. A byte-identical saved full RESULT is definitive proof that the whole atomic apply already completed, regardless of later state that superseded its postconditions: make no mutation and return the existing commit/outcome plus its still-pending calls and fresh frontier resolution. Never restore old postconditions during replay. Different RESULT content under the same session-id is a logical collision. A history/LOG mismatch is state inconsistency and routes to repair; an interrupted uncommitted apply is discarded by the mandatory fresh-worktree reset and then applied normally.
- **Deterministic merge operations:**
  - `preserve unchanged` or an unnamed field: keep the fresh current value.
  - add/upsert a list or map entity by stable id: absent means add; existing means merge field-by-field. Preserve current-only changes, apply RESULT-only changes, and treat identical changes as a no-op; a field changed on both sides follows the scalar rule below.
  - remove by stable id: remove the fresh current entity. If absent, same-RESULT replay is a no-op; a different recorded consumer is a logical collision.
  - explicitly set a scalar: use true three-way comparison. If RESULT equals base, keep current; if current equals base, apply RESULT; if current equals RESULT, no-op; if both changed differently, bounce as a semantic collision. `updated:` alone is always last-applier-wins. Clear/upsert `open_calls` by stable call id: different ids merge even inside one track, while competing meanings for the same call follow the scalar rule. Ignore any delta that only targets the removed global selector; it has no state authority and cannot collide with another track. Final merged state must still pass binding evidence, owner-verdict and hard-gate checks.
  - append LOG/history: key by session-id/history path and write once; identical existing content is a no-op, different content under that identity is a collision.
  - create a complete work/CALL file: absent means create, byte-identical means no-op, different existing content is a collision unless the RESULT explicitly declared a patch to that file.
- Reject CHARTER.md/TREE.md changes whose RESULT carries no `owner_approved` mark (gate G9) — reply with the missing approval instead of applying.
- Validate before applying (gate G10) — bounce with the specific miss, never apply partially:
  - RESULT fields complete per os/schema/packets.md, `play_check` included (one line per play step);
  - when current NOW uses lane-mode or state_changes introduce tracks, every RESULT/CALL/decision names an existing lane, or one declared in the same RESULT by `shape` (creation) or dissolved by `review` (closure); a lane created or removed by any other play, or an undeclared/ambiguous lane, bounces;
  - lane-mode NOW hygiene: without an active bet, tasks are empty, no non-recurring execution track/CALL exists, and at most one untracked `frame|map|converge|converge-arch|converge-verify|shape|review|repair` CALL is the planning frontier. The sole extra frontier may be `to: session, play: work`, without track/task, whose `for` resolves to a parked TREE node marked `outcome_kind: specification`; it is owner-authority planning, not execution. With tracks, a positive owner-approved `track_wip_limit` caps lanes with non-paused roots/decisions; ids/normalized labels are unique; every non-recurring `for` resolves to the current bet node/task; every call/decision names an existing lane; each lane has at most one parentless root; every child resolves a same-lane parent, appears in `waiting_on`, and has acyclic ancestry; every lane has a root or decision; statuses/artifacts/conditions are valid. New/retired lane or WIP-limit changes cite owner words. A return clears only its registered call and preserves unrelated lanes/calls;
  - **launch bookkeeping** — a work RESULT may change existing matching CALLs across lanes `ready -> running` only when its evidence/play_check cites the owner's exact launch words or a resolvable runtime claim receipt, and `running -> ready` only from exact lost/cancelled words or a runtime cancel receipt. **A dedicated writer is ephemeral - never a standing chat.** A repo-resident day chat may perform its writer half only after an explicitly saved day RESULT. It finishes apply/commit, rereads fresh state for the next leg, and carries no unsaved integration judgment.

**Concurrency.** Parallel directions use one workflow worktree each; within one direction RESULTs apply one at a time and merge independent calls/lanes by stable id. A queued RESULT may have stale bases and is semantically rebased when its turn arrives. Sync/push rules: `os/adapters/worktrees.md`.

- **Contract-pin override for collect/audit/digest (v29+).** For `collect`, an integer-pinned CALL compares the product
  stamp to that pin, not to a later global current; an older same-leg pin is never upgraded. A pre-v29 unversioned or
  `legacy:` CALL receives no Re-sync blocker. A behind stamp permits only the bounded `re-sync:<N>` install for N; it
  still blocks a new feature root pinned to N. A missing/unreadable stamp blocks both. In `audit` and
  `digest`, `vN < current` means "Re-sync owed before the next new root"; it is never evidence against an in-flight
  return. These rules supersede only the retroactive reading of the three earlier drift bullets.

### Frontier command rules

These clauses define multi-workstream resolution without a stored global selection:

- `collect next for <direction>/<track>` resolves that lane's sole lawful ready call/decision; direction resolves the sole actionable item; id resolves directly. Several return choices/recommendation. Non-ready calls are reported, never launched; outside-bet calls must match a lawful planning frontier (including specification authoring/verify/review) or route to repair/review.
- In lane-mode, audit requires an active bet, positive WIP limit, every non-recurring lane/call/decision serving that bet, unique ids/labels, one root/lane, acyclic child graph, valid status evidence, and a root/decision per lane. Without a bet, any non-recurring lane is drift. It also validates issues and direction forecast.
- `digest` renders one compact lane line plus direction forecast, due issues and future-objective count; it remains read-only.

## Role 2: executor (kind: engineering)

Receives a business task CALL targeting a product repo (`repo:` field). The full engineering process — plan gate, autonomous build, validation gates, retry/escalation, final report — is defined in `os/engineering/CONTOUR.md`; repo bootstrap in `os/engineering/PROJECT_SETUP.md`. The contract summary:

Contract:
- The CALL gives goal / context / boundaries / done_when / return / budget. The agent owns everything else: design, implementation, refactoring, branch/PR mechanics.
- Repo-internal conventions (build, test, style, architecture rules) live in that repo's AGENTS.md / CLAUDE.md — command-first, written once per repo. The OS never duplicates them.
- **Execution authority is repo-local.** The CALL + product-repo `AGENTS.md`, frozen plan/spec, the v23 frozen
  carrier where applicable, and `validation.config` define the workflow and its required tools. A globally
  installed/discoverable skill or tool is support, not authority: it cannot replace the workflow or add project
  requirements. The required-tool STOP below applies only after one of those repo authorities explicitly requires the
  tool; discovery or installation alone is never a blocker.
- The run contract installed in the repo's root AGENTS.md at setup governs the run (roles, gates, retry/escalation). No run contract → the repo is uninitialized: stop and report — the first CALL for this repo is setup per `os/engineering/PROJECT_SETUP.md` (interactive: stack interview with the owner).
- Exit report (= the RESULT's evidence): descriptive commits or PR link, diff summary, output of the checks run (tests/build), explicit list of assumptions made, anything cut for budget.
- Routing follows the CALL pin: every v29/legacy stage returns HOME for Direction continuation; a v30-v35 root remains open while its repo runner launches separate fresh stages from committed receipts, and returns HOME only at gated REPORT, genuine ESCALATE or Direction-authorized REPLACED. Neither route asks the owner to construct a successor.
- "Done" is the CALL's done_when verified by a runnable check, not the agent's assertion. A task that can't carry a runnable check should say how it is to be verified instead — at CALL time, not after.
- Blockers surface early: if the task looks infeasible or 2x over budget, stop and report — a fast "blocked, because" is a good result; days of silent struggle are not. A required tool/harness being UNAVAILABLE (engine Editor not running, a needed MCP disconnected, headless-test license absent) is a blocker: STOP and tell the owner which tool to launch — never a workaround or crutch around it; any exception stands only on the owner's explicit written ack (CONTOUR ESCALATE).

## Sizing rule

One feature leg is one cohesive invariant/source-of-truth slice and ≤ a focused half-day. An approved root may contain several dependency-ordered legs; its v30-v35 repo runner, not the owner or Direction, sequences them. A mixed leg is split before PAIR-CANDIDATE.

## Running thinking sessions here too

Any OS play can run in an agentic CLI session instead of a chat app: the agent reads `os/KERNEL.md`, the play file, and `live/<dir>/NOW.md` itself, and can act as its own writer for state changes **only after emitting its RESULT** (one relay hop instead of two, or zero with an orchestrator). Recommended default for shape / review / pulse / repair, which are state-heavy; chat apps stay attractive for frame and long work dialogs.
