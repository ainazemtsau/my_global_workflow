## 1. Природа продукта

Zaratustra это операционная система для экспертов. Эксперт это AI с закреплённой
зоной ответственности, который живёт над файлами владельца. Владелец
разговаривает с центром, центр раздаёт работу экспертам и собирает результаты.
Мозг это файлы, модели это сменные думающие руки: руки меняются, мозг остаётся
и растёт.

Принципы, закреплённые владельцем:

- Новый чистый продукт, преемник workflow. Не надстройка и не доработка.
- Строго индивидуальное использование: один владелец. Никаких команд, ролей и
  общих рабочих мест. Это позволяет сущности «владелец» быть ровно одной и не
  проектировать многопользовательность.
- Открытый исходник движка возможен; личные данные никогда не покидают
  приватное рабочее место.
- Продукт умнеет с новыми моделями, потому что всё мышление в моделях, а всё
  знание и структура в файлах и инструментах.

## 2. Ядро

### 2.1 Пять сущностей

Каждая это файл с типизированной шапкой сверху и текстом ниже.

1. Владелец. Профиль, ценности, предпочтения, общая память о нём, его решения.
   Одна папка. Эксперт читает её только по объявленной ссылке.
2. Эксперт (в движке `agent`). Зона ответственности и всё своё: паспорт,
   состояние, инструкция с версиями, память, разрешённые инструменты,
   подэксперты. Папка, вложенность любая. Бывает большой (здоровье) и маленький
   (трекер веса внутри здоровья). Сама Zaratustra тоже эксперт: план дня,
   маршрутизация вопросов, починка.
3. Работа (`job`). Одна ограниченная задача для одного исполнителя: что
   сделать, какой контекст объявлен, уровень модели, вид результата. Сегодня
   одна работа это один чат; это настройка исполнителя, не ядра.
4. Событие (`event`). Запись о том, что произошло: запрос, результат, решение,
   проблема, метрика, слово владельца. Только дописывается. Единственная
   история системы.
5. Артефакт (`artifact`). Файл, который произвела работа и который должен
   жить: план, доска, документ, исследование, картинка, выгрузка для чужого
   чата. Сохраняется в репо и не теряется.

### 2.2 Реестр

Таблицы того, что подключено: исполнители и уровни, инструменты и их паспорта,
виды показа, триггеры, шаблоны экспертов, настройки дня, пороги. Новая
возможность это строка в реестре и папка плагина, не правка программы.

### 2.3 Шесть точек расширения

1. Шаблоны экспертов: область с подэкспертами, трекер, проект, рутина, фоновый
   исследователь и любые новые.
2. Инструменты: базовые (в ядре), общие (погода, календарь, GitHub, поиск),
   свои у эксперта. У каждого паспорт: вход, выход, класс побочного эффекта,
   кому разрешён.
3. Исполнители: Claude Code, Codex, дешёвая модель по ключу, фоновый демон,
   человек.
4. Поверхности: командная строка, MCP в агенте владельца, ящик для ChatGPT web,
   веб-доска, Telegram.
5. Виды: план дня текстом, доска, виджеты, график, цитата на утро.
6. Триггеры: запрос владельца, время, событие.

Ядро меняется только если появляется шестая сущность. Известные случаи, которые
потребовали бы правки ядра нарочно, с версией и миграцией: прямое общение
экспертов мимо центра (нарушает правило 3); правда не в файлах. Многопользовательность
исключена решением владельца.

### 2.4 Шесть правил

1. Пишет только программа. Любое изменение состояния идёт командой, команда
   проверяет файл по схеме. Руками файлы не правятся ни человеком, ни моделью.
2. Журнал только дописывается. Ничего не удаляется, только заменяется новой
   версией. Откат это возврат версии.
3. Эксперт видит только своё и объявленное. Читает чужое только по ссылке из
   паспорта, пишет только в свою папку. Общая память приходит по ссылкам.
4. Результат работы типизирован. Длинный текст уходит в артефакт. Владельцу
   показывают вид, а не простыню из чата.
5. Программа не думает, думают эксперты. Всё без фантазии (проверка, очередь,
   сбор контекста, план дня) делает программа; всё с суждением делает эксперт по
   инструкции. Ядро не знает ни одной модели по имени.
6. Слово владельца включает. Необратимое, внешнее, платное действие и смена
   инструкции эксперта только после его слова, записанного событием.

### 2.5 Открыто для расширения, закрыто для правки

Поля ядра в шапках фиксированы. Шаблон или плагин добавляет свои поля под
собственным префиксом и объявляет их в реестре; инструмент проверяет и те и
другие. Виды событий: короткий закрытый список ядра, шаблон регистрирует свои под
своим именем. Инструменты: паспорт в реестре, любая модель зовёт одинаково.

Доказательство расширяемости: второй эксперт, второй инструмент, вторая
поверхность, второй вид добавляются с нулём изменений в файлах ядра, и это
видно диффом. Тронуть ядро ради добавления это дефект ядра.

## 3. Слои информации и загрузка контекста

| Слой | Что это | Кто пишет | Когда читается | Потолок |
|---|---|---|---|---|
| Состояние | следующее действие, ждёт владельца, проблемы, метрики | инструмент по команде агента | всегда, при любой работе эксперта | один экран; инструмент отказывает писать больше |
| Память | что верно сейчас; файл на тему; у владельца и у каждого эксперта | инструмент «запомнить» по типизированному факту из работы «разбор» | по темам, объявленным работой | каждый факт ссылается на события-источники |
| Артефакты | сами вещи | инструмент по результату работы | только по ссылке | нет |
| Журнал | что произошло, когда, кто | инструменты автоматически; агенты одной строкой | никогда по умолчанию; только через команду чтения с фильтрами | файл на день на эксперта |

Рабочий набор работы = состояние + объявленные темы памяти + объявленные
артефакты. Инструмент собирает его сам, печатает список с размерами до чтения
и отказывает сверх бюджета, который стоит в реестре для уровня модели. Это
механическая защита от «28 тысяч слов на любой запрос».

## 4. Журнал

- Физика: папка событий у каждого эксперта, файл на день. Файл не растёт
  бесконечно, завтра новый файл.
- Формат: строки JSON, одна запись на строку. Поля: время, уровень, вид, кто,
  работа, ключ, текст до 200 знаков, ссылки на артефакты. Все поля кроме текста
  закрытые списки. Читается только через команду, которая рендерит понятный
  текст; владелец файлы не читает.
- Три уровня: технический (пишут только инструменты), рабочий (агенты одной
  строкой: сделано, решение, заметка, слово владельца), проблемы (агенты с
  ключом проблемы).
- Автоматика: каждая команда, меняющая состояние, пишет технический след:
  команда, кто вызвал, работа, начало, конец, длительность, тронутые файлы и их
  хеш. Из этого считаются метрики.
- Проблемы: модель даёт проблеме ключ, инструмент считает одинаковые ключи;
  второй повтор создаёт работу «починить». Инструмент текст не понимает.
- Чтение: одна команда с фильтрами (эксперт, даты, уровень, вид, работа, слово,
  число строк), ограниченный ответ. Сводки за период это артефакт, который
  делает модель отдельной работой.
- Рост: команда статистики, порог в реестре, при превышении план дня ставит
  работу «архивировать»; старые месяцы переезжают в подпапку архива вне поиска
  по умолчанию; ничего не удаляется. Cron не нужен, пока нет демона.
- Утро: план дня читает вчерашние файлы всех экспертов на рабочем уровне и
  уровне проблем, несколько десятков строк.

## 5. Инструменты

- Инструмент проверяет форму и делает механику; смысл делает модель.
- Умеет: проверить схему и закрытые списки, существование ссылки, права и
  бюджет; записать, переместить, посчитать, отфильтровать; вернуть
  типизированный ответ.
- Никогда: не суммирует, не классифицирует, не извлекает факты из текста, не
  маршрутизирует по содержанию, не правит текст. Понимание текста это работа
  модели, возвращающая типизированный объект; инструмент проверяет его форму.
- Одинаковость: один инструмент для всех моделей и поверхностей, один формат
  файла, одна строка журнала. У каждого инструмента тест, где он отказывает на
  неверном входе. Тест, что программа выдаёт ровно команды протокола.
- Всё через инструменты: в Claude Code и Codex правка файлов рабочего места
  запрещается настройкой прав; каждая запись инструмента подписана хешем в
  техническом следе; команда проверки находит неподписанные изменения и
  показывает их как «правка мимо инструментов».

## 6. Репозитории, установка, обновление, запросы

- Публичный движок: Python-пакет `zaratustra`, команда `zara`, MCP-сервер,
  схемы, шаблоны экспертов, миграции, документация для ассистентов, образцовое
  рабочее место для тестов. Версии по правилу «главная.новая.починка», релизы
  с тегами. Личных данных нет.
- Публичный шаблон рабочего места: входная инструкция для Codex и Claude Code,
  файл зависимостей с закреплённой версией движка, файл-замок для `uv`,
  пустые папки.
- Приватное рабочее место владельца: создаётся из шаблона кнопкой GitHub.
  Код движка в нём не лежит, стоит зависимостью в окружении. Свои инструкции,
  шаблоны, настройки это данные владельца, переживают обновление. Частные
  возможности живут в папке плагинов и подхватываются через реестр.
- Установка: клонировать, открыть в Codex или Claude Code; ассистент читает
  входную инструкцию и запускает `uv sync --locked` и `uv run zara init`;
  `init` выдаёт ассистенту список вопросов первого запуска, тот задаёт их
  владельцу в чате и записывает ответы инструментами; генерирует настройки MCP;
  `zara guide` печатает, как работать. Никаких окон, одинаково на Windows и
  macOS.
- Обновление: `zara upgrade` закрепляет новую версию, ставит окружение, делает
  коммит рабочего места, прогоняет миграции сначала вхолостую, потом
  по-настоящему, каждая пишет след; печатает «обновлено с X на Y, миграции
  такие, что нового для ассистентов»; перегенерирует служебный блок входной
  инструкции между метками. Откат: возврат коммита и прежней версии. В шапке
  каждого файла номер схемы; при расхождении команда проверки отказывается
  работать и называет команду.
- Заметки к релизу в двух разделах: для владельца и для ассистентов.
  Инструкции ассистентов приходят из установленной версии движка (`guide`,
  описания инструментов в MCP, служебный блок), копий нет.
- Запросы на функционал: команды запроса в протоколе нет. Владелец приходит в
  Solmax сам и говорит, чего не хватает. Другие пользователи открывают issue в
  публичном репозитории движка сами.

## 7. Форматы файлов

Файлы в репозиториях только для ассистентов. Владелец читает через чат, потом
через виды и дашборды. Поэтому: тексты, которые читают модели, это markdown с
YAML-шапкой; машинные потоки (журнал, индексы) это строки JSON; индексы и кэши
разрешены как производные и пересобираемые, вторая правда запрещена.

полировка установки для чужих. Плагины после волны 6 или раньше при реальной
нужде. Содержание здоровья (меню, программа) пишется внутри волны 3 с
владельцем, не заранее.

## 9. Как Solmax ведёт эту работу

Четыре коротких чата, от владельца два «да»:

1. review: закрыть активную ставку «Первый полезный Health-срез». Рекомендуемый
   вердикт obsolete: решение владельца 2026-09-03 сняло её цель. Salvage как
   улики, без переноса структуры: `work/health-context-model-v1.md`,
   `work/health-workflow-svod-dnya-v1.md`, приём «одна команда проверки плюс
   selfcheck» из продуктового репо. Старый репозиторий
   `C:\projects\zaratusta-product` остаётся историей, в него больше не пишем.
2. frame (ревизия устава): миссия остаётся; меняются три вещи: Zaratustra это
   преемник workflow; два репозитория (публичный движок, приватное рабочее
   место); ветка operating-substrate закрывается. Критерии успеха: владелец
   ведёт через Zaratustra игру и хотя бы одну область жизни каждый день; другой
   человек ставит и обновляет её без нас; новая возможность это плагин с нулём
   правок ядра по диффу. Принцип индивидуального использования в устав.
   Показать разницу одним экраном.
3. map: семь целей = волны 0–6, все parked, активна одна. Правило направления в
   карту: спека любой цели это CORE.md, converge для целей не запускается
   (триаж trivial, `converge OFF — because CORE.md is the spec`). Узлы 2–6
   старой карты и operating-substrate закрываются или переписываются в волны.
4. shape волны 0 → работы по полдня → executor CALL в новый публичный
   репозиторий движка.

Дальше: одна активная цель, работы в продуктовом репозитории по полдня, чаты
берут их подряд, владелец говорит «продолжаем» и читает наискосок. С волны 2
Solmax выдаёт один CALL на волну, а внутри продукта работа идёт через
собственную очередь Zaratustra.

Что держит качество без внимания владельца:

- механика в репозитории движка: одна команда проверки, контроль красноты
  каждого гейта, границы модулей, тест отказа у каждого инструмента, тест
  «ровно команды протокола», проверка подписи записей;
- свежая проверка чужим чатом (Codex) на каждом изменении, три вопроса, любое
  «да» это отказ: появилась ли шестая сущность; понимает ли инструмент
  содержимое; есть ли запись мимо инструментов;
- проверка владельца по волне: сценарий на пять минут записан в цели заранее;
  волна закрывается только его результатом;
- светлое закрытие для всего, что перевыводится из байтов; свежий чат только
  там, где нужно суждение о поведении;
- стоп-правила: волна вышла за размер в полтора раза → стоп и вопрос
  владельцу; проверка владельца дважды не прошла на одной волне → стоп и
  перечитать CORE.md, не добавлять; команда вне протокола → сборка красная;
- модели: планирование и сборка Claude Code, свежая проверка Codex, механика
  позже на дешёвой полосе; одна линия работы, чтобы не отнимать чаты у игры.

Что делает владелец: «да» на устав и карту; «да» на CORE.md; пять минут в конце
каждой волны; приходит в Solmax, когда чего-то не хватает. Всё остальное:
«продолжаем».

## 11. Чего не делать (уроки истории направления)

- Не копировать структуру старых пакетов (health-reclamation, process-creator,
  operating-substrate, старый zaratusta): идеи и функционал можно, структуру нет.
- Не давать инструментам понимать текст. Не давать моделям править файлы мимо
  инструментов.
- Не отдавать владельцу на проверку контракты и схемы: он проверяет поведение
  сценарием на пять минут.
- Не создавать Health-содержание без владельца: специалист сочиняет, владелец
  подтверждает словом до активации.
