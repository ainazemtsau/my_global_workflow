## ЧАСТЬ 1 — предложение исполнителя, дословно

Я бы реализовал не два, а четыре чётко разделённых слоя.

### 1. LootDefinition — что это за предмет

Один `ScriptableObject` на каждый тип предмета:

```
LootDefinition
  DefinitionId           стабильный числовой ID
  DisplayName            «Ящик с инструментами»
  PhysicsProfile         ссылка на физический профиль
  VisualProfile          модель/prefab, пока может быть пустым
  BehaviorProfile        поведение, пока None или Alarm
```

В нём не должно быть:

* комнаты;
* координат;
* конкретного места появления.

Один и тот же `LootDefinition` можно будет поставить в десяти разных местах и разных домах.
`DefinitionId` — не индекс массива и не `CargoId`. Перестановка assets или строк не должна менять
идентичность предмета.

### 2. LootPhysicsProfile — как предмет ведёт себя физически

Отдельный переиспользуемый asset:

```
LootPhysicsProfile
  ProfileId
  Mass
  Collider Size
  Collider Center
  Center Of Mass
  возможно позже: трение, упругость, grip points
```

На первом этапе туда мигрируют существующие профили:

* Small — 48 кг;
* Medium — 100 кг;
* Large — 240 кг.

Количество требуемых игроков не записываем вручную. Inspector вычисляет и показывает ожидаемое число
носителей из массы, гравитации и силы рук.

Если одному конкретному предмету нужна другая масса:

1. Дублируем профиль.
2. Меняем массу.
3. Назначаем новый профиль только его `LootDefinition`.

Никаких mass override в раскладке. Иначе один и тот же тип предмета начнёт случайно весить по-разному
в разных комнатах.

### 3. LootCatalog — реестр определений

Catalog содержит ссылки на все `LootDefinition` и проверяет:

* уникальность `DefinitionId`;
* отсутствие пустых ссылок;
* наличие физического профиля;
* уникальность `ProfileId`;
* валидность массы и размеров;
* доступность visual/behavior profile.

Ошибки должны останавливать запуск Host с понятным сообщением, а не молча подставлять первый класс,
как сейчас.

### 4. LootSpawnLayout — где лежат экземпляры

Это scene-owned компонент, потому что раскладка относится к конкретному дому:

```
LootSpawn
  LootDefinition
  Room
  LootSupport
  Local X/Z Offset
  Initial Rotation
```

Порядковый номер spawn-записи пока остаётся runtime `CargoId`. `DefinitionId` обозначает тип
предмета, `CargoId` — конкретный экземпляр в текущем матче.

Например:

```
CargoId 6
DefinitionId 120 — Food Crate
PhysicsProfile 2 — Medium, 100 kg
Support — Kitchen/Floor
```

### LootSupport вместо ручного Y

Это ключевая часть.

На полу, столе, тумбе или полке будет `LootSupport`, связанный с настоящей физической поверхностью:

```
LootSupport
  Collider или физическая плоскость
  допустимая область размещения
  локальная ориентация
```

Spawn хранит положение относительно опоры, а не абсолютный мировой `Y`.

```
LootSupport вычисляет точку поверхности
       +
PhysicsProfile вычисляет расстояние от pivot до нижней грани
       =
правильная позиция физического тела
```

Для текущего пола надо также исправить саму геометрию: верх видимого пола и физический Collider
должны совпадать. Иначе spawn можно поставить правильно, но после поднятия и отпускания предмет снова
провалится до старого Collider.

То есть `Y=0.03` не понадобится.

### Runtime и сеть

Правильная цепочка будет такой:

```
SceneLootSpawnLayout
        ↓
LootDefinition
        ↓
LootPhysicsProfile
        ↓
Host создаёт CargoState
  CargoId
  DefinitionId
  PhysicsProfileId
  ThingState
  Pose
        ↓
Cargo Body — скрытая физика
        ↓
CargoSnapshot
        ↓
Client по DefinitionId выбирает модель
```

В `CargoState` и `CargoSnapshot` нужно добавить `DefinitionId`.

Это лучше сделать сейчас. Пытаться на клиенте угадывать модель по `CargoId` или `CargoClassId` —
хрупкий shortcut: он сломается при случайной раскладке, повторении одного типа, динамическом spawn и
позднем подключении клиента.

Unity-ссылки на prefab в сеть не отправляются. По сети идёт только стабильный числовой ID, а клиент
находит соответствующий asset в своём `LootCatalog`.

### Модели

В `LootDefinition` будет необязательная ссылка на visual profile/prefab.

На первом этапе:

* модели можно оставить пустыми;
* текущий куб остаётся fallback;
* spawn и сеть уже знают `DefinitionId`;
* позже модель добавляется в definition без изменения физики и раскладки.

Физическое тело и визуальная модель остаются раздельными. Это полезно: модель может быть сложной, но
авторитетная физика остаётся простой и детерминированной.

### Поведения

В definition будет ссылка на behavior profile:

```
None
AlarmClock
PaintCan — позже
...
```

Host по `BehaviorId` выбирает правило. Уже существующий `CargoThingState` хранит состояние конкретного
экземпляра, а snapshot передаёт его клиентам.

Первый этап не обязан реализовывать краску. Он должен только сделать правильную точку расширения:

* один definition выбирает поведение;
* раскладка ничего о поведении не знает;
* добавление нового поведения не меняет spawn pipeline;
* состояние принадлежит конкретному экземпляру.

Текущий будильник выбирается по весовому классу, что неправильно: сейчас любой предмет класса `0`
потенциально считается будильником. При миграции поведение надо связать с definition. Чтобы не менять
игровой смысл без отдельного решения, можно временно сохранить существующую семантику через
`LegacyAlarm`, а конкретный будильник выбрать позже.

### Что войдёт в первую реализацию

Я предлагаю такой законченный scope:

1. `LootDefinition`, `LootPhysicsProfile`, `LootCatalog`.
2. Scene-owned `LootSpawnLayout` и `LootSupport`.
3. Миграция текущих десяти предметов без изменения состава 5/3/2.
4. Исправление физического пола, чтобы Collider совпадал с видимой поверхностью.
5. `DefinitionId` в host state и network snapshot.
6. Inspector, показывающий: имя; фактическую массу; размеры; ожидаемых носителей; visual profile;
   behavior profile; опору и комнату.
7. Понятные runtime-названия вроде `Cargo Body 6 · Food Crate · 100 kg`.
8. Cube fallback без создания художественных моделей.
9. Валидация отсутствующих и повторяющихся ID.
10. Тесты layout → definition → physics → snapshot → presentation lookup.

Пока не входят: реальные модели; пятна краски; новые звуки и VFX; повреждение; стоимость;
процедурная генерация.

Но после этой работы всё это будет добавляться через definitions и profiles, без переписывания
spawn-системы.

Реализацию нужно оформить отдельной инженерной задачей. Текущий WIN-U1 уже содержит завершённый
кандидат `e0a30194…` и занят старым lease; расширять его новым сетевым и scene scope нельзя. Нужно
либо сначала завершить его WIN-CTRL handback и освободить WIN-U1, либо явно выбрать другой доступный
`WIN-U2`, `WIN-U3` или `WIN-U4` для нового CALL. Код в этом обсуждении я не менял.

## ЧАСТЬ 2 — ревью Направления, 2026-08-13

### Вердикт: ПОДХОДИТ ПО ФОРМЕ. Не подходит по размеру и содержит одну ошибку против подписанного выреза.

### Что в ней по-настоящему хорошо

**1. Громкая валидация вместо тихой подстановки.** Сегодня при плохих данных Host молча подставляет
первый класс. Это ровно тот класс дефекта, который уже висит в направлении открытой уликой
`i-broken-profile-rejection-never-observed-001`. Предложение чинит его как побочный эффект, и это
настоящая ценность, а не украшение.

**2. `LegacyAlarm` — правильная дисциплина.** Исполнитель заметил ошибку игрового смысла и ОТКАЗАЛСЯ
чинить её молча, предложив сохранить существующую семантику под названным временным именем и отдать
выбор владельцу. Это признак, которому можно доверять.

**3. Разделение тип / экземпляр и идентичность не индексом.** Прямо отвечает словам владельца, на
которых куплена задача: «у нас груз, это должен быть какой-то интерфейс, который потом либо
расширять, добавлять функционал».

### СРОЧНАЯ НАХОДКА: замороженный кандидат породил бы ПЯТЬ БУДИЛЬНИКОВ

Перемерено чтением байтов на `origin/main` = `c485b30e`:

- `Settings/GameRulesSettings.asset:70` → `_alarmCargoClassId: 0`.
- `Core/Cargo/AlarmClockCargoThing.cs:37-42` → `InitialStateFor(cargoClassId)` возвращает `Armed`
  тогда и только тогда, когда `cargoClassId == _cargoClassId`.
- `Settings/GameRulesSettings.cs:195-196` → это вызывается при создании КАЖДОГО груза.

Замороженный кандидат ставит **пять** предметов класса `0` (Bedside Radio, Kitchen Timer, Hall Key
Box, Remote Control, Desk Clock). Значит опубликуйся он как есть — в доме появилось бы пять
заведённых будильников вместо одного.

**Исполнитель прав, и он сформулировал мягче, чем есть на самом деле.** Это не «потенциально
считается» — это гарантированное срабатывание на пяти предметах, и оно ломает закрытую `t-thing-1`.

**Следствие для разреза: привязку будильника к определению НЕЛЬЗЯ откладывать.** Она обязана ехать в
той же задаче, что и десять предметов.

### ОШИБКА ПРОТИВ ПОДПИСАННОГО ВЫРЕЗА: реестр поведений

Вырез 9 ставки, подписанный владельцем: «ОБЩАЯ СИСТЕМА ИНТЕРАКТИВНЫХ ПРЕДМЕТОВ — второй новый слой,
запрещённый порогом 4 и уставом… Вместо неё — ОДИН предмет с состоянием и гейт на расширяемость».

`BehaviorProfile` с реестром `None / AlarmClock / PaintCan / …` и диспетчером `Host по BehaviorId
выбирает правило` — это и есть общая система. Она же превращает обещание волны «ноль новых слоёв» в
неправду и подводит под порог смерти 4.

**Урезать до одной строки:** будильник привязывается к КОНКРЕТНОМУ определению вместо весового
класса. Реестра поведений, диспетчера и `PaintCan` в этой волне нет. Точка расширения уже проверена
и закрыта `t-thing-1`; второй раз её строить не надо.

### Четыре правки поменьше

**1. Inspector не должен сам вычислять число носителей.** Ступень по рукам `144 / 300 / 720` Н —
закон, и карточка задачи прямо запрещает её переизобретать. Inspector, считающий носителей из массы,
гравитации и силы рук, — это ВТОРАЯ реализация закона, которая начнёт врать, как только разойдётся с
решателем. Он обязан спрашивать тот же production-код, что и игра, либо показывать сырое число рядом
с порогами.

**2. Исправление пола — сначала ИЗМЕРИТЬ, потом чинить.** Утверждение «верх видимого пола и Collider
не совпадают» Направлением не проверено. Оно правдоподобно, но это дом, а не лут, и лечится оно в
геометрии дома. Наряд обязан требовать числа до правки — тем же замком, каким прошлый наряд требовал
измерить цену коллизий, и это сработало.

**3. Не забыть четыре legacy-точки появления.** Прошлая нога измерила на живом прогоне: удаление
четырёх старых `CargoSpawnPoint` ломает контракт инвентаря компонентов лаборатории, и их пришлось
вернуть инертной заглушкой. Новая раскладка обязана сказать, что с ними делает. В предложении этого
нет.

**4. Блокер, из-за которого всё и встало, в предложении не упомянут вовсе.** Покоящийся предмет стал
твёрдым, но его окно контакта не читается пока он лежит и не сбрасывается при подъёме — накопленный
удар выстреливает протухшим шумом позже, и с приехавшим зрением этот ложный шум ранга `3` побьёт
настоящее увиденное ранга `2.5`. Без этой починки новая структура так же не опубликуется, как старая.

### Замечание про слот УСТАРЕЛО

Исполнитель пишет, что WIN-U1 «занят старым lease». Перемерено 2026-08-13 в
`gascoop-slot-state.v1.json`: **все четыре слота `AVAILABLE`, `lease none`.** Аренда отпущена. Выбор
слота свободен.

Отдельно: **база нового наряда — `origin/main`, а не замороженный кандидат.** Новая структура
заменяет библиотеку целиком, поэтому перебазироваться на устаревшую форму дороже, чем заново
завести десять строк. Замороженный кандидат идёт ВХОДОМ: список из десяти предметов, его измерения и
правка твёрдости с её измеренной ценой `66.548` мс на `10 240` шагов.

### РАЗМЕР — главная проблема, и её решает только владелец

Задача волны по правилу ≤ полдня, потолок контракта — три строки `done_when`. Здесь: три новых типа
ассетов, компонент сцены, система опор, правка сетевого состояния и снапшота, починка геометрии пола,
привязка поведения, инспектор, миграция и тесты. Прошлая нога построила МЕНЬШЕ и вернулась паузой.

Аппетит волны — одиннадцать задач, и `t-loot-1` названа первым кандидатом на вылет. Но его же слово
2026-08-13: «ничего выкидывать не надо».

**Рекомендация Направления — разрезать на две, ничего из волны не выкидывая.** Перерезка
существующей задачи не есть вход новой, а порог смерти 3 считает расход НА ЗАКРЫТУЮ задачу, поэтому
две настоящие закрытые задачи арифметику не портят.

- **Задача 1 — «поставил, и оно работает».** Определения, физические профили, каталог с громкой
  валидацией, раскладка в сцене, опоры вместо ручного `Y`, миграция десяти предметов, куб-заглушка,
  инспектор, тесты. Плюс две вещи, которые нельзя отложить: **починка окна контакта** и **привязка
  будильника к определению**. Это то, что владелец увидит глазом.
- **Задача 2 — идентичность по сети.** `DefinitionId` в состоянии и снапшоте, выбор модели клиентом
  по нему. Отдельно, потому что это сетевой авторитет, и он заслуживает своего отката.

**Довод исполнителя против такого разреза честный и его надо знать:** он говорит, что `DefinitionId`
дешевле добавить СЕЙЧАС, одним движением вместе с переписыванием, чем возвращаться потом. Это верно.
Разрез стоит примерно одного лишнего касания того же кода — и покупает за это отдельный откат на
сетевом слое, который в этом проекте ещё ни разу не трогали задачей про предметы.
