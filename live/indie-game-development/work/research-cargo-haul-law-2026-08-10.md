## 1. ЗАКОН, ВЫПИСАННЫЙ ЦЕЛИКОМ

Читано первой рукой: `Assets/TunnelCrew/Core/Cargo/CargoHaul.cs` (blob `9621b2ad7c75`),
`CargoRules.cs` (`15b303d7d9bd`), `CargoPull.cs` (`b56ca363be01`),
`AuthoritativeCargoRoster.cs` (`25802a44a9c5`), `Assets/TunnelCrew/Network/CargoBody.cs`
(`44591618ac0e`), `CargoBodyContact.cs` (`6dfac0c4124f`), `NetworkPlaySettings.asset`
(`d6b186f8a10a`), `ProjectSettings/TimeManager.asset`, `ProjectSettings/DynamicsManager.asset`.

### 1.1 Одна рука

```
s_i      = |T_i − G_i|                                  // T_i — точка рук держателя, G_i — хват в мире
effort_i = max(0, s_i − HandReach) · HandStiffness
F_i      = unit(T_i − G_i) · effort_i
Cap(F_i, MaxHandForce)                                  // ПОТОЛОК ЗДЕСЬ, внутри HandForce
```

`G_i` = `CargoGeometry.ToWorld(cargo, hold.GripX, hold.GripZ)` — хват хранится в собственной
системе груза, поэтому поворот груза уносит хват с собой. `T_i` = `HandPoint(CarryOffset)` —
точка в `0.8 м` впереди по взгляду держателя, обновляется каждый тик (`RefreshHoldTargets`).
Рука только ТЯНЕТ и никогда не толкает.

### 1.2 Как складываются руки — потолок стоит НА РУКЕ, до суммы

```
F = Σ_i F_i − LinearDamping · v            (демпфирование ОДИН раз на тело, не на руку)
τ = Σ_i (armZ_i·F_i.x − armX_i·F_i.z) − AngularDamping · ω
```

`Cap(...)` — последняя строка `HandForce`, а `forceX += handX` идёт уже после возврата. Значит
**каждая рука обрезается своим потолком отдельно, а СУММА не обрезана ничем: потолок пары равен
`N · MaxHandForce` и растёт по N линейно.** Комментарий в коде фиксирует и вторую половину:
демпфирование принадлежит телу целиком, «иначе двоих демпфировало бы вдвое сильнее одного без
причины, которую игрок мог бы назвать». Закон написан на список ЛЮБОЙ длины — «движок никогда не
видит держателя».

Точка приложения (`AtPoint`) выбирается так, чтобы воспроизвести суммарный момент, и прижимается
к предмету на радиус `√(HalfLength² + HalfWidth²)` = `0.0981 м`; невыразимый остаток уезжает в
`CargoPull.Torque` чистым поворотом.

Разрыв хвата (`ShouldRelease`) меряется от ТЕЛА держателя, не от руки: поворот головы хват не
рвёт, уход ногами рвёт.

### 1.3 Второе демпфирование, которое живёт в движке — и о нём легко забыть

`CargoBody.Spawn` ставит телу ещё и `rigidbody.linearDamping = _cargoLinearDamping = 4`. Это НЕ
то же число, что `_cargoHaulLinearDamping = 350`. Полное сопротивление на установившемся ходу:

```
C(m) = HaulLinearDamping + λ·m ,   λ = (1/α − 1)/dt_тик ,   α = (1/(1 + d·h))^steps
d = 4 (1/с), h = 1/60 с, steps = 2  →  α = 0.87891  →  λ = 4.1333 1/с
C(20) = 350 + 82.67 = 432.67 Н на м/с
```

Наивная запись `F = m·d·v` дала бы `λ = 4.0` и `C = 430`; расхождение 3 %, ни один вывод от него
не меняется, но ниже стоит точное.

**Следствие, которое меняет ответ:** масса ВХОДИТ в установившийся баланс — через движковое
демпфирование, потому что оно пропорционально массе. Наивное «масса влияет только на разгон»
здесь неверно.

### 1.4 Интегрирование

Тик судьи `1/30 с` (FishNet `_tickRate = 30`, компонент нигде не сериализован — создаётся с
умолчанием). `ApplyPull` отдаёт `AddForceAtPosition(force · seconds, point, Impulse)` за ровно
один тик — **размерность в пути тяги верна, рассинхрона единиц там нет.** Затем `Physics.Simulate`
двумя подшагами по `1/60 с`. Порядок тика (`CarryWorld.Advance`): нагрузка → ходоки → груз →
доставка → хозяин → и только в конце шаг движка.

**Рассинхрон единиц есть в пути КОНТАКТА, и он подтверждён обоими выводами.**
`CargoBodyContact.Record` делит импульс на `Time.fixedDeltaTime = 0.02`, тогда как настоящая
длительность подшага `0.01667`. Все контактные усилия занижены в `0.8333` раза, то есть пороги
`60 / 150 / 400` фактически значат `72 / 180 / 480` настоящих ньютонов. Это уже заведённая улика
`i-noise-bands-invisible-and-force-mis-scaled-001`; здесь она НЕ чинится и на выводы ниже не
влияет, потому что коэффициент общий.

### 1.5 ВЕРТИКАЛИ В ЭТОМ ЗАКОНЕ НЕТ ВООБЩЕ

`CargoPull` несёт ровно пять чисел: `ForceX`, `ForceZ`, `PointX`, `PointZ`, `Torque` (поворот
вокруг вертикали). **Подъёмной силы в модели не существует.** Три независимых механизма делают
высоту константой:

```csharp
// AuthoritativeCargoRoster.Advance — присваивание, не сила
if (held) cargo.State = cargo.State.WithPose(cargo.State.X, rules.CargoCarryHeight, cargo.State.Z, cargo.State.Yaw);

// CargoBody.SetBodyActivity
if (held) { position.y = _settings.CargoCarryHeight;            // 0.092
            rigidbody.linearVelocity = new Vector3(velocity.x, 0f, velocity.z);
            rigidbody.constraints = TiltConstraints | RigidbodyConstraints.FreezePositionY; }

// CargoBody.Step — гравитация прикладывается ТОЛЬКО неудерживаемому телу
if (body.Active && !body.Held) AddForce(Vector3.down * CargoGravity, ForceMode.Acceleration);
```

Один налётчик мгновенно поднимает на `0.092 м` груз любой массы — 20 кг, 20 000 кг, безразлично.
Точка «сумма вверх пересекает `m·g`» не существует: числителя нет, знаменатель отключён.

Число держателей вообще смотрят ровно в трёх местах, и ни одно не про высоту:
`cargo.Holds.Count > 0` (булево «держат»), `Holds.Count >= limit` (потолок набора),
`snapshot.HolderCount > 0` (цвет на клиенте). Больше N нигде не участвует — только как длина
цикла суммирования.

## 2. ЧТО ЭТО ДАЁТ НАБЛЮДАЕМОГО ПРИ N РУКАХ — СЕГОДНЯ

Установившийся баланс: `N · MaxHandForce = C(m) · v`, при `m = 20` знаменатель `432.67`.

| N | предельная скорость волочения | нужно на руку при ходьбе 0.36 м/с | отставание груза от точки рук |
|---|---|---|---|
| 1 | **0.462 м/с** | 155.8 Н из 200 | **9.4 см** |
| 2 | 0.925 м/с | 77.9 Н из 200 | **5.5 см** |
| 3 | 1.387 м/с | 51.9 Н из 200 | 4.2 см |
| 4 | 1.849 м/с | 39.0 Н из 200 | 3.6 см |

**Первый вывод, и он неприятный: сегодня одна рука уже справляется полностью.** Ей нужно 155.8 Н
из 200 доступных, чтобы держать груз на полной скорости несущей мыши. Узкое место — НОГИ мыши
(0.36 м/с), а не луч. Разрыв хвата не наступает ни при каком N (`0.89 м` против предела `1.6 м`).

**Второй вывод: «вдвоём» не делает груз послушнее — оно делает его пружинистее.** Эффективная
жёсткость `N·2000` против той же вязкости `432.67`:

| N | ω, рад/с | коэффициент затухания ζ | что это на глаз |
|---|---|---|---|
| 1 | 10.0 | **1.082** — передемпфировано | приходит и встаёт намертво |
| 2 | 14.14 | **0.765** — недодемпфировано | перелёт ≈ 2.4 % |
| 3 | 17.3 | 0.625 | перелёт 8 % |
| 4 | 20.0 | 0.541 | перелёт 15 % |

**Третий вывод: единственное место, где разница 1 / 2 видна уже сегодня, — БЫСТРЫЙ ПОВОРОТ.**
Точка рук ездит по окружности радиуса `0.8 м`, поэтому поворот со скоростью ω гонит хват со
скоростью `0.8·ω`. Одна рука упирается в потолок при

```
ω > 0.462 / 0.8 = 0.578 рад/с ≈ 33°/с
```

двое — при 67°/с, трое — при 100°/с, четверо — при 133°/с. Мышь поворачивается быстрее 33°/с
постоянно. То есть на резком развороте груз у одиночки заносит и он тянется следом, а у двоих
догоняет вдвое быстрее. Проверяемо как время обхода дуги при развороте на 90° (~2.7 с у одного).
Это настоящая наблюдаемая по сети разница — но она про ПОВОРОТ, а не про ВЕС.

**Четвёртый вывод: «чем больше взялись, тем ВЫШЕ идёт груз» не даёт ни одно число** (§1.5).

**Сводка для брифа: «вдвоём» сегодня не даёт ни скорости (0.36 м/с в обоих случаях), ни высоты
(0.092 м в обоих), ни послушности (становится чуть пружинистее) — только 3.9 см меньшее
отставание и вдвое более высокий порог заноса на повороте.**

## 3. ТРИ ВАРИАНТА ЧИСЕЛ — С ЧЕСТНОЙ ЦЕНОЙ, БЕЗ ВЫБОРА

Общая механика всех трёх: сделать так, чтобы спрос при `v = 0.36 м/с` превысил потолок ОДНОЙ руки
и не превысил потолок ДВУХ. Отбор по неравенству

```
N · MaxHandForce  <  (HaulLinearDamping + λ·m) · MovementSpeed · CarrySpeedScale
```

Все три остаются внутри границ `t-scale-6`: ни поштучных размеров/массы (`t-scale-7`), ни личной
мощности хвата (`t-scale-7`), ни порогов шума, ни телекинезных `1.28 / 0.8 / 1.6`.

**Сразу и честно про N=3 и N=4: во всех трёх вариантах они неотличимы от N=2.** Как только пара
держит полную скорость ног, третья и четвёртая рука не добавляют ни скорости, ни высоты.
Поднять `_cargoMaxHolders: 2 → 4` нужно, чтобы четверо ВООБЩЕ могли взяться; наблюдаемого это
само по себе не добавляет.

### Вариант «П» — слабее рука: `_cargoMaxHandForce` `200 → 120`

| N | предельная скорость | успевает за мышью (0.36)? | отставание |
|---|---|---|---|
| 1 | **0.277 м/с** | **НЕТ** — 77 % скорости, груз отстаёт всё сильнее | растёт на 0.083 м/с |
| 2 | 0.555 м/с | да | 5.5 см — ровно как сегодня вдвоём |
| 3 | 0.832 м/с | да | 3.7 см |
| 4 | 1.109 м/с | да | 2.7 см |

**Цена.** Масса, пороги шума, падение, ω, ζ — не тронуты. Стоя на месте и при мелких доворотах
одиночная переноска **побайтово та же**, что владелец принял руками: потолок не достигается, пока
растяжка меньше `0.016 + 120/2000 = 0.076 м`. Меняется только режим ДВИЖЕНИЯ. Риск, названный
прямо: одиночка, идущий НАЗАД, роняет груз через ~9.6 с непрерывного хода (обрыв по
`GripLength`), идя вперёд — через ~29 с. Это ровно тот «отказ только на скорости, читающийся как
загадка», о котором предупреждает комментарий в `CargoRules.GripLength`. Плюс: именно этот потолок
в `t-scale-7` становится ЛИЧНОЙ мощностью хвата — сегодняшнее общее число там станет умолчанием.

### Вариант «М» — тяжелее груз: `_cargoMass` `20 → 90`

`C = 350 + 4.1333·90 = 722`; спрос при 0.36 м/с = 260 Н.

| N | предельная скорость | успевает? | отставание |
|---|---|---|---|
| 1 | **0.277 м/с** | **НЕТ** | растёт на 0.083 м/с |
| 2 | 0.554 м/с | да | 8.1 см |
| 3 | 0.831 м/с | да | 5.9 см |
| 4 | 1.108 м/с | да | 4.8 см |

Порог перехода точный: одна рука перестаёт успевать при `m > 49.7 кг`, двое — при `m > 184.1 кг`.
**Сегодняшние 20 кг лежат в 2.5 раза НИЖЕ нижней границы полосы «нужны двое».**

**Цена, и она большая.** `CargoBodyContact.Record` докладывает
`force = collision.impulse.magnitude / Time.fixedDeltaTime`, а импульс контакта пропорционален
массе. Учетверение с лишним массы **умножает на 4.5 каждое доложенное усилие контакта против
замороженных порогов `60 / 150 / 400`**: тычки, сегодня беззвучные, станут шорохом и стуком, и
хозяин начнёт приходить на то, на что не приходил. Чтобы шум остался прежним, пороги надо
двигать на `270 / 675 / 1800` — три числа, которые эта задача трогать не вправе. Плюс отклик
замедляется вдвое: `ω = 4.71` вместо 10, груз ходит за взглядом вальяжнее. Это ровно то, о чём
предупреждает `knowledge/scale-down-raises-mass.md`: массу в этой игре определяют пороги шума, а
не плотность. **Внутри границ этой задачи цену заплатить нечем.**

### Вариант «В» — вязче тяга: `_cargoHaulLinearDamping` `350 → 900`

`C = 982.67`; спрос при 0.36 м/с = 353.8 Н.

| N | предельная скорость | успевает? | отставание |
|---|---|---|---|
| 1 | **0.204 м/с** | **НЕТ** — 57 % скорости | растёт на 0.156 м/с |
| 2 | 0.407 м/с | да, но впритык (запас 13 %) | 9.45 см |
| 3 | 0.611 м/с | да | 7.5 см |
| 4 | 0.814 м/с | да | 6.5 см |

**Цена, самая дорогая по ощущению.** `ζ(N=1) = 2.46` — сильно передемпфировано: стоя на месте и
просто крутя головой, владелец увидит, что груз ПОЛЗЁТ, а не идёт (успокоение ~1.5 с). Второй
риск структурный: при N=2 растяжка `9.45 см` против насыщения руки `11.6 см` — запас всего 19 %,
и стоит одному из двоих чуть отстать или потянуть под углом, как его рука упирается в потолок и
пара проваливается ниже спроса. Одиночка, идущий назад, роняет груз через ~5.1 с.

## 4. ДОПУЩЕНИЯ

1. Все таблицы — **установившийся** режим, а не замер прогоном.
2. Тик `1/30 с` взят из умолчания FishNet `TimeManager._tickRate = 30`: компонент нигде не
   сериализован, ни одна сцена его не переопределяет. Если он где-то настраивается в рантайме,
   все числа со временем поплывут.
3. Демпфирование PhysX принято как `v ← v/(1 + d·h)` за подшаг, отсюда `λ = 4.1333`. Наивная
   форма `m·d·v` даёт `λ = 4.0` и сдвигает границы с `49.7 / 184.1 кг` на `51.4 / 190.3 кг`.
   Ни один вывод от этого не меняется.
4. Оба держателя считались тянущими в одну сторону и делящими усилие поровну. Под углом θ друг к
   другу доступное вдоль хода = `2·F·cos(θ/2)`, и все строки «вдвоём» надо умножить на `cos(θ/2)`.
5. Ввод цифровой (клавиши), поэтому носильщик либо стоит, либо идёт ровно 0.36 м/с —
   промежуточных скоростей, на которых «П» была бы неотличима от сегодняшнего, в игре нет.
6. Момент инерции `I_y = 0.0641 кг·м²` вычислен из габаритов и массы; Unity считает тензор сам,
   значение должно совпасть, но замерено не было.
7. Хват мыши считался идеально ведущим: мышь идёт прямо, точка рук впереди на `0.8 м`. Стена,
   проём и другой лут в расчёт не входили.

### Расхождения с прежними документами — названы, а не унаследованы

- Продуктовый `docs/results/c-exec-g-5a7c-scale-probe-001.md` утверждает установившуюся тягу
  **126 Н** и коэффициент затухания **0.875**. Оба числа считаны без вклада
  `_cargoLinearDamping: 4`, который тело реально чувствует (`CargoBody.Spawn` присваивает его
  явно). Правильные величины: **155.8 Н** и **ζ = 1.082**, то есть система передемпфирована, а не
  слегка недодемпфирована. `ω = √(2000/20) = 10 рад/с` в том документе верно.
- Разбор `t-scale-4` писал, что масса влияет только на `k/m` и `F/m`. Это верно для ядра и неверно
  целиком: движковое демпфирование пропорционально массе и потому входит в установившийся баланс.
  Правильный знаменатель — `(350 + 4.1333·m)`.
- Тот же продуктовый документ упоминает `mass 50`; асcет на типе говорит `_cargoMass: 20`. Права
  версия асcета.

## 5. ЧЕСТНЫЙ ПРОБЕЛ И ВОПРОС ВЛАДЕЛЬЦУ

**Однозначного режима под названную текстуру НЕТ, и причина не в числах.**

«Лёгкий груз несёт один, средний — двое» требует, чтобы в одной сцене лежали ДВА РАЗНЫХ груза.
Сегодня все куски лута — один и тот же кусок: `_cargoLength/_cargoWidth/_cargoHeight/_cargoMass`
лежат одним комплектом на всю игру, `CreateCargoRules()` возвращает ОДИН `CargoRules` на всех, а
`CargoBody.Spawn` берёт те же четыре числа для КАЖДОГО тела; `_additionalCargoSpawns` — это только
координаты. Поштучные числа — это и есть шов «класс груза», **вырезанный из этой волны в
`t-scale-7`** (улика `i-bigger-loot-needs-the-cargo-class-seam-001`, его собственный выбор «Оба
варианта А» = следующей волной).

Значит внутри `t-scale-6` можно выбрать только, ГДЕ на шкале стоит сегодняшний единственный лут:
оставить его «лёгким» — и тогда разницы «один / двое» на прямой ходьбе не будет вообще; или
сделать «средним» — и тогда лёгкого лута в игре не будет до `t-scale-7`, потому что средним
станет ВЕСЬ лут разом. Обе половины фразы одновременно не покупаются ни одним числом.

**Второй пробел, отдельный:** «чем больше взялись, тем ВЫШЕ идёт груз» не покупается ничем —
высота несомого груза константа с замороженной осью Y, а подъёмной силы в модели не существует
(§1.5). Это не настройка, это отсутствующий закон. Вертикаль переноски владелец сам откладывал
раньше — улика `i-cargo-carry-open-questions-001` несёт его «возможно вообще не решать».

**Третье, которое надо знать при обсуждении:** если «лёгкий / средний» на самом деле про
НАЛЁТЧИКОВ, а не про предметы, то нужный шов другой — `CargoHold.Strength` уже едет в каждом
хвате и просто не читается (§1.6). Это тоже код и тоже `t-scale-7`.
